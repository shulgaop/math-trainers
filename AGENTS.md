# AGENTS.md — правила для Kimi Code

## Назначение проекта

Русскоязычный учебный сайт для ребёнка и взрослого, который проверяет ответы. Объяснения должны быть простыми, решения — пошаговыми, тренажёры — действительно интерактивными.

## Перед началом каждой итерации

1. Прочитай `README.md`.
2. Прочитай `CONTEXT.md` — это текущее состояние проекта.
3. Прочитай последнюю запись в `CHANGELOG.md`.
4. Если задача относится к существующей странице, сначала прочитай соответствующий HTML целиком или хотя бы изменяемый раздел и весь связанный JavaScript.
5. Не полагайся на историю чата как на единственный источник контекста: проект должен восстанавливаться по файлам.

## Архитектура

- Исходники сайта: только папка `site`.
- `site/index.html` — главная страница о пропорциях.
- `site/procenty.html` — проценты и разборы задач.
- `site/luch.html` — координатный луч и десятичные дроби.
- `site/videos/` — локальные MP4-ролики и JPG-обложки; папка обязательна для публикации вместе с HTML.
- `.github/workflows/deploy.yml` — CI/CD: проверка и автоматическая публикация `site` на GitHub Pages из `main`; Pull Request только проверяется.
- `tests/validate_site.py` — проверка страниц, локальных ресурсов, якорей и JavaScript без сторонних Python-пакетов.
- `DEPLOYMENT.md` — первичная настройка GitHub Pages, обновление, откат и диагностика.
- `docs/GRAPHS.md` — графы архитектуры, публикации и зависимостей учебных тем; обновлять при изменении связей.
- HTML, CSS и JavaScript намеренно хранятся в каждой странице: проект должен оставаться статическим и работать без сборки.
- Не добавляй React, npm, backend, базу данных или обязательные внешние библиотеки без отдельного запроса пользователя.
- Ссылки между страницами должны оставаться относительными: `index.html`, `procenty.html`, `luch.html`.
- Не помещай в `site` служебные документы, исходные фотографии учебника, архивы или временные файлы.

## Требования к содержанию

- Пиши по-русски, понятным школьнику языком, без канцелярита.
- Не выдавай готовый ответ без объяснения: показывай признак типа задачи, действия и проверку, где она полезна.
- Сохраняй формат раскрывающихся решений через `<details>` и `<summary>`, чтобы ребёнок мог сначала решить сам.
- Проверяй математику независимо: вручную, через точные дроби или отдельный расчёт. Не используй собственный генератор как единственное доказательство правильности его ответов.
- В текстовых генераторах следи за русскими формами слов и единицами измерения.
- Для процентов различай три целых: исходное число, остаток и новое целое в последовательных действиях.

## Требования к интерфейсу

- Сохраняй существующую тёплую дизайн-систему, адаптивность и читаемость.
- Новые элементы управления должны работать; декоративные неактивные кнопки запрещены.
- Поля числовых ответов должны принимать запятую и точку как десятичный разделитель.
- Во всех тренажёрах сохраняй «Мои ошибки»: исходное задание, последний неверный ответ, закрытый разбор и повторное решение. Верный повтор удаляет задание из списка. Список хранится только в памяти страницы; для луча при повторе восстанавливается исходная SVG-схема.
- Не устанавливай автофокус при загрузке страницы: на телефоне это может прокрутить страницу сразу к тренажёру.
- Сохраняй `:focus-visible` и поддержку `prefers-reduced-motion`.
- Видео встраивай через нативный `<video controls playsinline preload="metadata">`, без автозапуска; обложки и ролики храни локально в `site/videos`.
- На ширине 375 px не должно быть горизонтальной прокрутки.

## Проверка после изменения

Запусти локальный сервер из папки `site` и проверь реальную страницу в браузере:

1. Нет ошибок и необработанных исключений в консоли.
2. Открываются все три страницы и работают перекрёстные ссылки.
3. Новые `<details>` раскрываются и закрываются.
4. В затронутом тренажёре проверены правильный ответ, неправильный ответ, подсказка и кнопка нового задания.
5. Проверены несколько сгенерированных заданий, включая граничные случаи.
6. Проверен мобильный вид 375 px и десктопный вид.
7. Длинные дроби, формулы и условия не выходят за карточки.
8. После изменения видео проверены HTTP-загрузка MP4/JPG, метаданные, реальное воспроизведение со звуком, пауза и отсутствие автозапуска.

Если автоматическая браузерная проверка недоступна, честно запиши это в журнал и перечисль, что пользователю нужно проверить вручную. Никогда не пиши «проверено», если проверка не выполнялась.

## CI/CD и публикация

- Перед завершением итерации запускай `python3 tests/validate_site.py --require-node` в WSL/Linux или `py tests\validate_site.py --require-node` в Windows PowerShell.
- Публикуемые файлы находятся только в `site`; не переноси документацию, тесты, фотографии и архивы в публичный артефакт.
- Не отключай проверки ради прохождения workflow. Исправь источник ошибки.
- Не меняй триггер так, чтобы Pull Request или другая ветка могли публиковаться без отдельного согласования.
- Сохранение версии сайта в Kimi, успешный локальный тест и успешный `validate` не являются публикацией. Публикацией считается только успешный `deploy` на GitHub Pages или фактически проверенный внешний хостинг.
- Не утверждай, что GitHub Actions выполнен, если репозиторий не подключён или запуск не наблюдался.

## Обязательные данные после каждой итерации

После **каждой** завершённой итерации, даже небольшой:

1. Обнови `CONTEXT.md`:
   - текущий состав страниц;
   - новые разделы, функции и типы заданий;
   - новые контрольные ответы;
   - актуальные ограничения и нерешённые вопросы;
   - дату и номер последней итерации.
2. Добавь новую запись в начало `CHANGELOG.md` по шаблону:

```markdown
## Итерация N — YYYY-MM-DD — короткое название

**Задача:** что просил пользователь.

**Изменённые файлы:** список файлов.

**Добавлено:** разделы, функции, формулы, типы генераторов и контрольные ответы.

**Проверено:** только реально выполненные проверки и их результат.

**Не проверено / ограничения:** если что-то осталось.

**Следующий шаг:** конкретное продолжение или «не требуется».
```

3. Убедись, что следующий агент сможет продолжить работу только по этим файлам, без поиска старого чата.
4. В ответе пользователю перечисли изменённые файлы, выполненные проверки и оставшиеся ограничения.

## Пакет для хостинга

При подготовке нового пакета копируй в `site` только конечные HTML-файлы и необходимые статические ресурсы. Не включай `.git`, скриншоты, временные проверочные скрипты, кэши и пользовательские загрузки. Полный архив должен содержать `site`, `.github/workflows`, постоянные тесты из `tests`, `.gitignore` и актуальные Markdown-документы. В архиве только для хостинга достаточно содержимого `site`.
